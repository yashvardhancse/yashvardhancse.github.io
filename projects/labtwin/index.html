LabTwin — a browser digital twin of a lab robot

Write a protocol, get it checked line by line, watch a deterministic 3-axis simulation in 3D, and record or replay every run as an MCAP file that opens in Foxglove — backed by a real ROS 2 (rclpy) package that shares the same interfaces.

  • TypeScript
  • React + three.js
  • ROS 2 / rclpy
  • Python 3.13
  • MCAP + Foxglove
  • Docker + CI
Live demo Source on GitHub How it maps to ROS 2

LabTwin is a digital twin of a robot that prepares cryo-EM samples by placing a few nanolitres of liquid onto a chilled grid. You write a protocol in YAML, the editor checks it line by line, and a deterministic 3-axis simulation plays it back in 3D — while every run is recorded to an MCAP file that also opens in Foxglove. Everything runs client-side in the browser, and a real ROS 2 (rclpy) package shares the same message interfaces, so a recording written by the Python/ROS 2 side replays in the browser twin.

Why it fits robotics & lab automation

I built LabTwin around the exact problems a small robotics-software team faces when automating a benchtop instrument — the hardware/controller boundary, reproducible runs, and tools scientists can actually use.

  • ROS 2 & topic design

    Nodes that model the machine

    A real rclpy package (labtwin_msgs: AxisState/PumpState messages, a MoveTo action, and services) plus browser nodes — gantry_driver, pump_driver, stage_controller, protocol_executor — that talk over the same typed topics.

  • MCAP + 3D model

    Record & replay runs

    Every run is recorded to MCAP with JSON Schemas, and carries /tf, /scene and /log against Foxglove's official schemas, so a 3D panel shows the moving gantry. Live and replay go through one render path.

  • Operator tooling

    Protocols scientists can trust

    A YAML editor with live validation: unknown steps, types and ranges, axis/speed/volume/temperature limits, ordering rules ("home before moving", "stage cold before dispensing") and physical warnings — each pointing at the exact token with a fix.

  • Builds, containers, CI

    Reproducible and tested

    A pinned toolchain and a multi-stage Docker image. CI runs lint, 85 web unit tests, a build, an MCAP interop check, and a separate ROS 2 job that colcon builds on the official ros:jazzy image and runs 17 Python tests. Both simulators are bit-for-bit deterministic.

  • C++ / PLC boundary

    Drive bridge (roadmap)

    The next step is an rclcpp node modelling the CODESYS/EtherCAT boundary: the trajectory and servo run on the PLC at the fieldbus cycle, while ROS 2 commands it and reads state — the same split a real drive stack uses.

  • Review & docs

    Written to be read

    Strict TypeScript with a type-aware ESLint boundary (src/core can't import React, three.js or the DOM), a ruff-linted, pytest-tested Python package, small reviewable commits, and an architecture document that records the trade-offs.

Catching mistakes before the machine moves

The protocol editor validates as you type. Pick the "broken protocol" example and eight planted mistakes are underlined, each with its line number and a fix; the run button stays disabled until they are resolved. The executor also re-checks the important preconditions at run time — a dispense holds until the stage is actually cold, and aborts if it never gets there.

One render path for live and replay

The key design decision is that the 3D view, the charts and the run report render only from recorded topics — never from the simulator's internals. A live run and a replayed MCAP file go through exactly the same code, so if a run renders live, its recording replays. That is also what makes the browser twin and the Python/ROS 2 side interchangeable.

Interoperating with real ROS 2

Because both sides share topic names and JSON Schemas, a run recorded by the Python/ROS 2 package opens and replays in the browser twin — the 3D machine, charts and report all follow the Python-recorded state. The ROS 2 workspace builds on the official ros:jazzy image in CI and runs a node smoke test.

Try it

Open the live demo — a run starts by itself: the head homes, the stage frosts over while it draws 4 nL from the vial, then writes a 3 nL droplet onto the grid. Download the .mcap, re-open it to scrub the timeline, or drop it into Foxglove. The full build, test and ROS 2 instructions are in the repository.
