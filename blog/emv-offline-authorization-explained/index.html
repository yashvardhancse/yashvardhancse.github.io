Key takeaways

  • In EMV offline authorization the card approves with a TC without asking the issuer in real time. The terminal asks; the card may agree or tighten, never loosen.
  • An online-capable terminal compares its five-byte TVR with action codes and requests a TC, an ARQC (go online) or an AAC (decline).
  • The floor limit is terminal data (tag 9F1B), not a card property.
  • With no connection after an ARQC, the Default action codes choose between offline approval and decline.
  • Offline PIN, offline data authentication and store-and-forward are different things.

EMV offline authorization is a chip payment approved without a real-time check by the issuer. The terminal compares its risk flags with action codes and asks the card for a TC (approve), an ARQC (go online) or an AAC (decline). The card may match or tighten that request.[1] An approved TC reaches the issuer later, in clearing.[2][3]

Note: Scope and sources

EMV is the chip-card standard maintained by EMVCo. This article paraphrases its Book 3 (application specification) and Book 4 (cardholder, attendant and acquirer interface requirements), version 4.4 (October 2022), read from third-party-hosted copies.[1][2] EMVCo bulletins up to August 2026 can change details. Books 1 and 2 were not read, so application selection and key cryptography stay high level. Not covered: ATMs, online PIN, issuer scripts, offline-only and online-only terminals. What is EMV offline authorization? Four things called "offline"

EMV offline authorization is a payment the terminal and chip complete without waiting for the issuer, the cardholder's bank. "Offline" is overloaded in EMV;[4] this article keeps four meanings apart:

  • Offline authorization. The card returns a TC to the first GENERATE AC and the sale completes without the issuer. The issuer sees it later in clearing, when the merchant's bank (the acquirer) submits its records.[3]
  • Offline PIN. The chip checks the PIN. It verifies the cardholder, not the payment.
  • Offline data authentication. The terminal checks the card's signed data, and sometimes the chip itself. It does not show the payment is approved.
  • Store-and-forward. The terminal or processor accepts the sale and requests authorization later. The issuer can still decline.

How does an EMV chip transaction work, step by step?

Terminal and card exchange commands; the issuer joins only if needed. Each data object has a hexadecimal tag, its identifier. We follow Book 3's order of functions.[1]

  1. Application selection. The terminal picks a payment application and its identifier.
  2. Initiate application processing. The terminal clears its TVR and TSI, sends GET PROCESSING OPTIONS (GPO) and gets back the AIP (tag 82, capability flags) and a file list (94).
  3. Read application data. READ RECORD returns the card number, expiry, CDOL1 and CDOL2 (the data GENERATE AC needs), the issuer action codes and offline limits.
  4. Offline checks, in any order. Offline data authentication (ODA), processing restrictions and cardholder verification (CVM). Failures usually set TVR bits instead of ending the transaction.
  5. Terminal risk management. Floor limit, random selection and velocity checks set more TVR bits.
  6. Terminal action analysis. The TVR is compared with the action codes to pick the request: TC, ARQC or AAC.
  7. First GENERATE AC. The terminal sends its request in P1. After its own risk checks the card returns the CID (9F27), the ATC (9F36, a transaction counter), a cryptogram (9F26) and optional issuer data (9F10). A TC or AAC ends it offline; an ARQC means go online.
  8. Online processing, normally only after an ARQC. The issuer replies with an authorization response code (ARC), possibly with Issuer Authentication Data (tag 91, holding the Authorization Response Cryptogram, ARPC) and scripts (tags 71, 72).
  9. Second GENERATE AC. The terminal asks for a TC (approved) or an AAC (declined) and the card answers with one.

This is a teaching order: Book 3 calls its flowchart only an example, and a CDA signature can be checked only once a GENERATE AC response has arrived (sections 8.2 and 10).[1]

ARQC vs TC vs AAC: what the three cryptograms mean

All three are 8-byte application cryptograms made by the card (tag 9F26, or inside the 9F4B signature with CDA): the AAC (Application Authentication Cryptogram, a decline), the TC (Transaction Certificate, an approval) and the ARQC (Authorization Request Cryptogram, a request to go online). The top two bits of the CID say which: 00 AAC, 01 TC, 10 ARQC; 11 is reserved (Book 3, Table 15).[1]

Table 1. With the other bits at 0, the CID byte and the P1 that requests it are equal. Add 0x10 to the P1 of a TC or ARQC request to ask for a CDA signature too.
CryptogramCID byte and P1Meaning
AAC0x00Card declines.
TC0x40Card approves. Answering the first GENERATE AC, it ends the sale offline; answering the second, it confirms an online approval. Either way it goes to clearing.
ARQC0x80Card asks for online authorization. The issuer verifies it.

The terminal cannot verify any of them. A cryptogram is a message authentication code (MAC), not a digital signature: in formal models the card computes it with a session key derived from the ATC and a secret key known only to the card and the issuer.[3]

Why the card has the last word

The results form a ladder: TC, ARQC, AAC. The card may answer with the requested rung or a lower one, never a higher one: a TC request can return any of the three, an ARQC request an ARQC or AAC, an AAC request only an AAC. The second GENERATE AC returns only a TC or AAC (Book 3, section 9.3).[1]

What the card checks is the issuer's business and invisible to the terminal. In Book 3's optional Common Core Definitions profile, for example, offline count and amount limits make the card force an online-capable terminal online past a lower limit and decline when online is impossible past an upper one (Part V).[1]

Myth: the terminal approves the payment

The terminal makes a preliminary decision. Even response code Y1 (offline approved) leaves the final decision to the card, though an attended terminal may force acceptance after an AAC where payment-system rules allow it (Book 4, sections 6.3.6 and 6.5.4).[2]

EMV floor limit and terminal risk management

Terminal risk management is three checks the terminal runs after it has read the card's records and before it sends the first GENERATE AC: floor limit, random selection and velocity. Each only sets TVR bits (Book 3, section 10.6).[1]

What is an EMV floor limit, and who sets it?

A floor limit is an amount held by the terminal. If the amount is equal to or greater than it, the terminal sets the TVR bit "transaction exceeds floor limit" (byte 4, 0x80). In EMV it is data object 9F1B, four bytes, kept per application and set under payment-system and acquirer rules.[1][2] A terminal that logs approved sales first adds the most recent logged amount for the same card number, which catches a purchase split in two, not a longer series.[1]

Warning: Not a card property

The card stores issuer preferences (action codes, optional offline limits), not a floor limit, and no value is universal: Visa's U.S. acquirer guide (June 2020) calls the U.S. a zero-floor-limit market for Visa transactions, so those go online. Other networks and later rules were not checked.[5]

Random selection and velocity checking

Random selection sends some small transactions online. A draw from 1 to 99 at or below the Transaction Target Percent selects the sale.[1]

P=(Pmax−Ptarget)×A−TF−T+Ptarget

Equation 1: Transaction Target Percent (Book 3, section 10.6.2)

In words: below the payment system's threshold the percentage is the target; above it, start at the target and add a share of the gap to the maximum, scaled by where the amount A sits between the threshold T and the floor limit F.

If the card holds both the Lower and Upper Consecutive Offline Limit (9F14, 9F23), the terminal reads the ATC (9F36) and the Last Online ATC Register (9F13, the ATC of the last online transaction) with GET DATA and takes their difference. A difference above the lower limit sets one TVR bit and above the upper limit another; one equal to the lower limit has not exceeded it.[1]

TVR, TAC and IAC: how the terminal chooses TC, ARQC or AAC

The terminal collects its findings in the five-byte TVR (tag 95) and compares it with three pairs of action codes. Each pair joins a Terminal Action Code (TAC, the acquirer's preference, held in the terminal) with an Issuer Action Code (IAC, read from the card). A pair fires when a TVR bit that is 1 is also 1 in the TAC or IAC: in at least one of the five bytes, TVR & (TAC | IAC) is non-zero (Book 3, section 10.7).[1] For an online-capable terminal, as in our examples, they are tested in this order (offline-only and online-only terminals differ):

  1. Denial pair (TAC-Denial, IAC-Denial 9F0E). If it fires, the terminal asks for an AAC and does not go online.
  2. Online pair (TAC-Online, IAC-Online 9F0F). If it fires, the terminal asks for an ARQC; otherwise a TC.
  3. Default pair (TAC-Default, IAC-Default 9F0D). Used only when the terminal wanted to go online and could not. If it fires, it asks for an AAC; otherwise a TC.

Book 3 strongly recommends that TAC-Online and TAC-Default include the TVR bits for failed or missing offline data authentication; otherwise a counterfeit card with all-zero issuer codes could have every transaction approved offline.[1]

Three worked examples: offline TC, online ARQC and no connection

One terminal, card and set of action codes give three outcomes. Every value is invented; real floor limits and action codes come from payment-system rules, acquirers and issuers.

  • Terminal: Terminal Type 22 (attended, merchant-controlled, offline with online capability; Book 4, Table 24). Floor limit 9F1B = 3000 (EUR 30.00, bytes 00000BB8; amounts are in cents). Random selection: target 10%, maximum 40%, threshold 1000 (EUR 10.00).
  • Card: lower offline limit 5, upper 10, Last Online ATC Register 39.
  • Action codes: TAC-Denial 0070000000, IAC-Denial zeros; TAC-Online CC00A09106, IAC-Online C000806000; TAC-Default CC00800106, IAC-Default 0000002000 (changed in 3b). Both TACs set the ODA-failure bits Book 3 recommends: byte 1 CC, byte 4 bit 01, byte 5 06.
  • Assumed: DDA or CDA and the processing restrictions pass and the CVM list is satisfied, so TVR bytes 1 to 3 and 5 stay zero.

Example 1: EUR 12.50 is approved offline with a TC

Floor limit: 1250 is below 3000, so that bit stays 0. It is above the 1000 threshold, so random selection is biased: factor (1250 − 1000) ÷ (3000 − 1000) = 0.125, target (40 − 10) × 0.125 + 10 = 13.75. The draw is 73, so the sale is not selected. Velocity: ATC 42 − 39 = 3, within the lower limit of 5.

The TVR stays 0000000000, so no pair fires and the terminal asks for a TC (P1 0x40, or 0x50 with CDA), recording response code Y1 (offline approved; Book 4, Table 35). The card agrees and returns a TC (CID 0x40). The TSI reads E800 (ODA, cardholder verification, card and terminal risk management)[1] and the TC is stored for clearing.[2] With an ATC of 46 the difference is 7, TVR byte 4 becomes 0x40, which the issuer's IAC-Online contains, so the terminal asks for an ARQC instead.

Example 2: EUR 45.00 is above the floor limit and goes online

4500 is at least 3000, so TVR byte 4 bit 0x80 is set: the TVR is 0000008000. Both Denial codes are zero in byte 4, so Denial does not fire. In Table 2 we run the Online test on byte 4 (b8 floor limit, b7 lower limit, b6 upper limit, b5 random selection, b1 XDA signature failed): combine the TAC and IAC with a bitwise or, then apply a bitwise and with the TVR.

The terminal asks for an ARQC (P1 0x80, or 0x90 with CDA) and the card returns an ARQC (CID 0x80). A second GENERATE AC asks for a TC if approved or an AAC if declined, and the card returns a TC (CID 0x40) for clearing (Book 3, sections 9.3.2 and 10.11).[1]

Example 3: no connection after an ARQC

Same EUR 45.00 sale, ARQC returned, request timing out. After any repeats the acquirer requires, the terminal treats the transaction as unable to go online and compares the TVR with the Default codes (Book 4, section 12.2).[2]

  • 3a. TAC-Default CC00800106 and IAC-Default 0000002000 share no bit with TVR byte 4 (0x80), so nothing fires. The terminal sets Y3 (unable to go online, offline approved) and asks for a TC, though the card can still answer AAC.
  • 3b. With IAC-Default 000000A000, which adds the floor limit bit, 0x80 & (0x01 | 0xA0) is 0x80: the pair fires, so the terminal sets Z3 (offline declined) and asks for an AAC.

SDA, DDA and CDA: offline data authentication in short

Offline data authentication lets the terminal check, with the payment system's CA public keys and the card's certificates, that the card's data (SDA) or the chip itself (DDA, CDA) is genuine. It is separate from approval.[1]

  • SDA (static data authentication). The issuer signed fixed card data (tag 93). It detects altered data, not a copied card.
  • DDA (dynamic data authentication). The card signs a fresh terminal challenge with its own key (tag 9F4B), proving the chip holds the key.
  • CDA (combined DDA and cryptogram generation). The signature also covers the cryptogram, inside the GENERATE AC response, so the terminal can detect tampering with the card's answer.
  • XDA (extended data authentication). Version 4.4 also defines this ECC-based method. It outranks the other three, and after an XDA failure even a TC can lead online (Book 3, section 10.9).

The terminal uses the strongest method both sides support; the AIP lists the card's methods (byte 1: 0x80 XDA, 0x40 SDA, 0x20 DDA, 0x01 CDA; Book 3, Annex C).[1] Under SDA or DDA the card never signs the TC, so only the issuer can notice tampering later. A 2021 formal analysis (IEEE S&P) found this gap and that CDA closes it, though only some CDA setups met all its goals, none with offline PIN; its models date from 2020-21, so current kernels may differ.[3]

Can contactless payments be approved offline?

Sometimes, but it is uncommon (a 2021 study saw none in more than 30 live payments),[3] and the rules are scheme-specific. A contactless payment runs on a kernel, the reader software of one payment system, and EMVCo says each global payment system has its own kernel specification, so Book 3's contact flow is a model, not a description of every tap.[6] Visa's U.S. guide (June 2020) describes qVSDC, where the card generates its cryptogram while handling GET PROCESSING OPTIONS, and fast DDA for readers that support offline contactless. It sets the reader's contactless floor limit to zero, so Visa contactless payments there go online.[5] Other kernels and phone wallets are out of scope.

Offline EMV vs store-and-forward, and card machines in flight

In offline EMV the card's TC is the approval. In store-and-forward the terminal or processor approves locally and asks the issuer later, so the issuer can still decline and the merchant usually carries the loss.[7][8] Offline EMV is not risk-free either, because the issuer first sees the TC in clearing, after the sale is over. Adyen tells its users they are fully liable for failed captures, chargebacks and disputes on payments they process offline.[8] Liability follows the acquirer contract and card network rules, so check them first. For store-and-forward queues and timing rules on aircraft, ships and trains, read how credit card machines work in flight without internet.

Trade reports of 8 and 9 October 2026 say Mastercard will enable offline payments on all newly issued Mastercard cards in Europe from February 2027 and require new and replacement terminals to support them by May 2027, with limits stored on the chip and set by the cardholder's bank.[9][10][11] None names EMV or a cryptogram, so ask your acquirer what applies to your terminals.

Frequently asked questions

Can a chip card payment be approved offline?

Yes, when the terminal and the card both support it and the checks pass. The terminal asks the card for a TC (Transaction Certificate). The card runs its own risk checks and returns a TC (approved), an ARQC (go online) or an AAC (decline). Whether this is allowed depends on terminal configuration and on payment-system and acquirer rules: Visa's U.S. acquirer guide (June 2020), for example, sets a zero floor limit for Visa transactions, so those go online.

What is the difference between ARQC, TC and AAC?

All three are 8-byte application cryptograms made by the card: the AAC (Application Authentication Cryptogram) declines, the TC (Transaction Certificate) approves and the ARQC (Authorization Request Cryptogram) asks for online authorization. The top two bits of the Cryptogram Information Data byte (tag 9F27) tell them apart: 00 is an AAC, 01 a TC and 10 an ARQC. Only the issuer can verify the cryptogram, and an approved TC reaches the issuer later through clearing.

What is a floor limit in EMV, and who sets it?

A floor limit is an amount held in the terminal (tag 9F1B) for each application and set under payment-system and acquirer rules. It is not stored on the card. In Book 3, if the transaction amount is equal to or greater than it, the terminal sets a TVR bit that the action codes normally turn into an online request; some glossaries say "above", so check the boundary in your own scheme's rules. A floor limit of zero sets that bit on every transaction.

What happens if the terminal wants to go online but has no connection?

After the card returns an ARQC and the online attempt fails, the terminal compares the TVR with the Default action codes from the terminal and from the card. If a TVR bit is also set in either Default code, the terminal asks for an AAC and sets response code Z3. Otherwise it asks for a TC and sets Y3. The card can still answer with an AAC.

Is offline PIN the same as offline authorization?

No. Offline PIN is a cardholder verification method: the terminal sends the PIN to the chip and the chip checks it. Offline authorization is the approval decision made without contacting the issuer. A payment can use an offline PIN and still go online, or be approved offline with no PIN at all.

What is the difference between SDA, DDA and CDA?

SDA (static data authentication) checks an issuer signature over static card data, so it detects altered data but not a copied card. DDA (dynamic data authentication) has the chip sign a fresh terminal challenge with its own key. CDA (combined DDA and cryptogram generation) also signs the transaction cryptogram, so the terminal can detect tampering with the card's answer. Version 4.4 also defines XDA, an ECC-based method that outranks the others when both sides support it.

Is offline EMV the same as store-and-forward?

No: in offline EMV the card decides locally and its TC is the approval. In store-and-forward the terminal or processor approves locally and sends an authorization request later, so the issuer can still decline and the merchant usually carries that risk. Offline EMV is not risk-free either, because the issuer first sees the TC in clearing. For the store-and-forward side, see how credit card machines work in flight without internet.

Can contactless payments be approved offline?

It depends on the payment system's contactless kernel and on how the reader is configured. Visa's U.S. acquirer guide (June 2020), for example, describes fast DDA for readers that support offline contactless transactions, yet sets the U.S. reader contactless floor limit to zero, so Visa contactless transactions there go online. Other kernels differ and are outside this article.
